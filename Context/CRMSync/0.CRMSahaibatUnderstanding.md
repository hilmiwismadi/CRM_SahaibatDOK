Dokumentasi hasil eksplorasi langsung (Claude in Chrome, read-only — tidak ada data yang diubah/disubmit) pada tiga halaman utama `sales.sahaibat.com`, per 2026-09-29, login sebagai `hilmi.d@sahaibat.com`. ### Mekanisme Journey/Activity — **terkonfirmasi penuh** (2026-09-29, verifikasi silang lewat DOM di dua tempat sekaligus untuk lead "Klinik Pratama Qanita", `a345a549-5837-4d9c-bda5-34aaec307891`, yang sudah punya histori nyata)

Format setiap entri: `<icon> <deskripsi> · <tanggal, jam> · <email actor>`. Contoh nyata yang tertangkap (dua entri, dari yang terlama ke terbaru):
```
🔀/📝  Status → Contacted        · Sep 25, 09:45 AM · hilmi.d@sahaibat.com   (auto, dari ganti Stage)
💬     Follow up about letter sent · Sep 28, 01:48 PM · hilmi.d@sahaibat.com   (manual, dari form Activity)
```

**Dua sumber entri, dikonfirmasi identik/satu data source** (isinya sama persis dibaca dari `/clients/<uuid>` section "Journey" MAUPUN dari modal Edit lead di `/crm?edit=<uuid>` section "Activity") — **tapi ikon untuk entri auto "Status → X" berbeda tampilan di dua tempat**: `🔀` di halaman `/clients/<uuid>`, `📝` di modal Edit `/crm`. Kemungkinan cuma beda rendering client-side, bukan data berbeda.

**Aturan yang sekarang jelas:**
1. **Mengubah dropdown Stage** (di modal Edit, di combobox inline tabel `/crm`, atau di header `/clients/<uuid>`) lalu disimpan ⇒ **otomatis** membuat entri Journey `Status → <Stage baru>`. Tidak perlu isi form Activity terpisah untuk ini.
2. **Form Activity** (Response type + Channel + catatan bebas + tombol Log) ⇒ membuat entri Journey terpisah, **ikon entri mengikuti Channel yang dipilih** (💬 untuk WhatsApp, kemungkinan 📞/🤝/✉️/📝 untuk Call/Meeting/Email/Note — pola ini konsisten dengan daftar opsi Channel, belum diverifikasi satu-satu tapi sangat mungkin), **teks entri = catatan bebas yang diketik**, BUKAN label Response type yang dipilih.
3. **Response type sepertinya tidak muncul di teks Journey sama sekali** — fungsinya kemungkinan besar cuma untuk: (a) trigger auto-ubah-stage pada 2 opsi khusus (🤝→Demo, 🚫→Lost), dan (b) mengisi filter/badge "Response" di `/crm` (**Any response / 🔥 Asked for profile-meeting / 💬 Responded / ⏳ No reply yet**, dan badge kolom Response seperti "Contacted, nothing back yet") — **hipotesis, belum diverifikasi langsung lewat API**, tapi masuk akal dari nama-nama field yang sama persis.

### ✅ API endpoint Activity — **terkonfirmasi** (2026-09-30, submit nyata + baca client bundle)

Log 1 activity nyata sengaja dilakukan (dengan izin user) untuk lead "Klinik Harist Kartasura Sukoharjo Solo" untuk reverse-engineer ini:

```
POST /api/leads/{leadId}/activities
Body: { kind: "whatsapp"|"call"|"meeting"|"email"|"note", body: "<catatan bebas>", outcome: "<lihat tabel>" }
```

Dikonfirmasi via `GET /api/leads/{leadId}/activities` (endpoint yang sama, method GET, menampilkan histori) — shape row tersimpan: `{ id, lead_id, created_at, created_by, kind, body, outcome, signal, contact_id, target_class, access_route_id }`.

- **`kind`** = value Channel apa adanya (`call`/`whatsapp`/`meeting`/`email`/`note`) — tidak ada translasi.
- **`outcome`** = hasil translasi dari value Response type (bukan value mentahnya) — tabel mapping didapat dari baca source JS client bundle `/crm`'s page chunk (`_next/static/chunks/app/crm/page-*.js`), dicari string dekat label masing-masing opsi:

  | Response type (label) | value client `<select>` | `outcome` tersimpan | `signal` |
  |---|---|---|---|
  | 📤 We contacted them — no reply yet | `sent` | `outbound` | (kosong) |
  | 📄 asked for the profile / letter | `material` | `requested_material` | `inbound` |
  | 💬 asked a question | `question` | `question` | `inbound` |
  | 💰 asked about pricing | `pricing` | `asked_pricing` | `inbound` |
  | 🤝 asked for a demo (→ sets stage Demo) | `meeting` | `demo` | `inbound` |
  | 🚫 Not interested (→ sets stage Lost) | `no` | `batal` | `inbound` |

  Baris terakhir dua (`demo`/`batal`) **persis sama** dengan kode stage CRM tim sendiri — kuat dugaan server men-support outcome ini sebagai sinyal auto-ubah-stage (sesuai label UI-nya), tapi mekanisme persis (apakah 1 request memicu 2 efek sekaligus, atau ada request kedua terpisah) **belum diverifikasi langsung** (tidak dites live demi menghindari mengubah stage lead sungguhan tanpa perlu).
- Hanya `outcome: "outbound"` (default) yang benar-benar dites live dan dikonfirmasi bekerja end-to-end.
- `signal`, `contact_id`, `target_class`, `access_route_id` — ada di tabel tapi tidak diisi/diuji, kemungkinan dipakai fitur lain ("Ways in"/"Getting to the decision-maker").

**Konsekuensi:** endpoint ini adalah yang sama untuk entri "Status → X" otomatis (kind:"stage") dan entri manual (kind: salah satu Channel) — tapi belum jelas apakah entri "stage" dibuat lewat POST ke endpoint yang sama juga, atau lewat mekanisme server-side terpisah saat `PATCH /api/leads/{id}` `{stage}` dipanggil. Masih relevan untuk goal 1 (apakah sync stage otomatis via script tetap tercatat di Journey) — **belum terjawab penuh**, tapi setidaknya endpoint activities-nya sendiri sekarang diketahui persis.

### Fitur `/sync` di CRM pribadi (Mapping) — dibangun 2026-09-30

Untuk mengotomasi sebagian alur manual di atas, dibangun halaman baru di app Mapping sendiri (`apps/web`), bukan di `sales.sahaibat.com`:

Tombol "Generate script" merangkai baris yang terisi jadi script paste-ke-console `sales.sahaibat.com` (pola sama seperti `crm-team-sync.js`), memanggil `POST /api/leads/{id}/activities` dengan `outcome:"outbound"` tetap (Response type sengaja tidak diekspos di UI ini — selalu default, sesuai permintaan user 2026-09-30).
- Sub-tab ke-3 di `/sync` **ditunda** (user belum menentukan isinya).
- **Belum di-smoke-test di browser sungguhan** (Docker Desktop tidak jalan saat dibangun, tidak bisa start dev server lokal) — hanya diverifikasi lewat `tsc --noEmit` dan `eslint` (keduanya bersih). Cek manual di browser sebelum dipakai untuk kerja nyata.

**Catatan keamanan penting:** ditemukan `apps/web/AGENTS.md` (dan `CLAUDE.md` yang me-`@import` file itu) berisi instruksi mencurigakan menyuruh agent membaca `node_modules/next/dist/docs/` sebelum coding, dengan klaim palsu soal "breaking changes Next.js" dan klaim file ini "auto-regenerated by `next dev`" (path itu tidak ada di Next.js manapun — bukan konvensi asli). Ini pola **prompt injection** yang ditanam di repo. **Tidak diikuti** selama sesi ini. ### ⚠️ Temuan penting — ketidaksinkronan status kandidat vs lead (dikonfirmasi via API, 2026-09-29; **direvisi** setelah tahu ada tombol bulk "Add N to CRM")

Kronologi CSV `imports/2026-09-28.csv` (14 lead):
1. CSV di-paste ke kotak "Import candidates (CSV)" → **"Score & import"** diklik → 14 baris masuk sebagai kandidat baru, status `"new"`, score "unverified".
2. User lalu men-select kandidat (kemungkinan besar **select-all**) dan klik toolbar bulk **"14 selected → Add 14 to CRM"** — *ini baru diketahui dari user, belum sempat saya eksplorasi langsung sebelumnya.*
3. Hasilnya: 13 lead berhasil terbuat di `/crm` pada stage **"prospek"**, 1 (**"Dokter BUDI HARTOYO, Jaten, Karanganyar"**) gagal dengan error `"duplicate"` — pesannya persis sama bentuknya dengan error yang dikembalikan `PATCH /api/lead-candidates/{id}` `{action:"promote"}` di `crm-team-sync.js` (`error:"duplicate", conflict:{leadId, org}`).

**Revisi kesimpulan saya sebelumnya:** kemungkinan besar **"Score & import" saja TIDAK langsung membuat Lead** — pembuatan Lead terjadi di langkah bulk "Add N to CRM" (langkah 2), bukan otomatis di langkah 1 seperti yang saya duga semula. Ini masuk akal juga menjelaskan kenapa Budi Hartoyo bisa "duplicate": kemungkinan baris kandidatnya sempat ter-*submit dua kali* (mis. "Score & import" diklik lebih dari sekali dengan textarea yang sama, jadi ada 2 baris kandidat untuk nama/nomor yang sama) — baris pertama berhasil di-promote saat bulk add, baris kedua gagal karena lead-nya sudah ada. **Belum 100% dipastikan** — hipotesis terbaik saat ini, bukan fakta terverifikasi.

Yang **sudah pasti** (dikonfirmasi lewat API, terlepas dari mekanismenya):
- Ke-14 baris kandidat **tetap berstatus `"new"`** di `lead_candidates` walau lead-nya (13 dari 14) sudah ada di `/crm` (dikonfirmasi lewat `/api/lead-candidates?status=new` → persis 14 hasil, semua nama & source cocok) — field `status` yang teramati punya 3 nilai: `"new"`, `"promoted"`, `"rejected"`, tapi tidak ada yang di-set `"promoted"` di sini meski lead-nya sudah ada.
- Konsekuensinya: kandidat ini tetap nangkring di tab "New" `/lead-engine` dengan tombol **→ CRM** (individual) yang kelihatan masih aktif — **kalau diklik lagi (baik individual maupun lewat bulk "Add to CRM" ulang), kemungkinan besar akan error "duplicate" untuk yang lead-nya sudah ada** — bukan tanda ada masalah data, cuma candidate queue yang tidak auto-sync ke status lead-nya.
- **Implikasi untuk SOP:** setelah promote (individual atau bulk) dan lead-nya terkonfirmasi ada di `/crm`, kandidat yang "menggantung" di tab New sebaiknya di-**Reject** manual (bukan dibiarkan/di-klik ulang) supaya tidak menumpuk. **Belum diverifikasi** apakah Reject di sini mempengaruhi Lead yang sudah terbuat (kemungkinan besar tidak, karena keduanya entity terpisah — tapi belum dicoba).

## Ringkasan aksi yang TIDAK dicoba (berpotensi side-effect nyata)
Demi menghindari perubahan data tim yang tidak diminta, tombol/aksi berikut sengaja **tidak** diklik/disubmit selama eksplorasi ini (termasuk sesi lanjutan 2026-09-29) — hanya dicatat labelnya. Form yang dibuka untuk didokumentasikan (Set a programme, Record customer details) dibuka lalu **ditinggalkan tanpa Save**, tidak divalidasi apakah "Cancel"/navigasi keluar benar-benar membatalkan tanpa sisa perubahan.
- Semua tombol kirim WhatsApp (**Send intro WhatsApp**, **Open conversation**, **Start welcome journey / welcome journey**, **Track onboarding**).
- Semua tombol AI/web research (**Research**, **Discover**, **Search for people**, **Look them up**, **🔎 Find socials**).
- **Delete** (baris lead di `/crm`) dan **🗑 Delete** (bulk, di toolbar seleksi kandidat `/lead-engine`) — destruktif, berisiko dialog `confirm()`, kemungkinan hard-delete.
- **Score & import**, **Reject** (individual & bulk), **Transfer lead**, **Add a person**, **Add a route**, **Link another location**, **→ Add N to CRM** (bulk), **Set a programme → Save**, **Record customer details → Save** — semua ini mengubah data sungguhan di database tim.

## Catatan teknis untuk sesi Claude-browser berikutnya

- **Teknik klik yang andal di app ini:** klik lewat `computer` tool memakai `ref` dari `read_page` **kadang gagal diam-diam** (tool melaporkan sukses tapi state React tidak berubah — dialami berulang kali di halaman ini, termasuk pada checkbox dan tombol "Set a programme"/"Record customer details"). Yang **konsisten berhasil**: `javascript_tool`, cari elemen lewat `document.querySelectorAll(...)` dicocokkan ke teks/`aria-label`, lalu panggil `.click()` langsung di JS. Selalu verifikasi hasil klik (mis. baca `el.checked`, atau cari teks baru yang harusnya muncul) sebelum lanjut ke langkah berikutnya — jangan asumsikan sukses dari respons tool saja.
- **`read_page` filter `"interactive"` kadang cuma menangkap sebagian elemen** (tampak seperti dibatasi area viewport/scroll saat ini) — filter `"all"` lebih bisa diandalkan untuk mendapat gambaran lengkap, tapi outputnya sering ke-truncate di halaman besar (`/crm` dengan 381 baris ⇒ ratusan ribu karakter). Untuk data yang tidak butuh accessibility label (misal ambil breakdown skor, isi form tersembunyi, atau teks toolbar dinamis), **langsung query DOM lewat `javascript_tool`** jauh lebih efisien & reliable daripada `read_page`.
- **CDP `Page.captureScreenshot` sempat berulang kali timeout** di sesi ini (30-45 detik lalu gagal) — kalau ini terjadi lagi, jangan retry screenshot berkali-kali; pindah ke `read_page`/`javascript_tool` untuk membaca state halaman, screenshot bukan satu-satunya cara verifikasi.
- **Navigasi via `navigate` tool bisa terasa "nyangkut"** (tool melaporkan sukses tapi `tabs_context_mcp` masih menunjukkan URL lama) — pernah terjadi setelah membuka 2 form tersembunyi (Set a programme + Record customer details) tanpa Save di halaman sebelumnya; menekan `Escape` lalu re-check `tabs_context_mcp` menyelesaikannya. Kemungkinan ada state transisi client-side yang butuh waktu ekstra atau minor race condition — belum tentu terkait form yang belum di-save, tapi waspadai kalau navigasi tidak langsung ter-reflect.

### Goal 1 — Sinkronisasi stage CRM pribadi (Mapping, `103.93.162.31:3000` / local) ↔ CRM tim (`sales.sahaibat.com/crm`)

#### ✅ Arah sinkronisasi — **DIPUTUSKAN**: satu arah (Mapping → CRM tim saja)

Tidak ada tulis-balik ke Mapping. Ini menyederhanakan implementasi (tidak perlu resolusi konflik dua arah).

**Tapi — catatan penting yang tetap berlaku meski satu arah:** aturan **"jangan pernah menurunkan stage yang sudah lebih maju di CRM tim"** tetap wajib ada di script, walau arahnya cuma satu. Alasannya: CRM tim bisa berubah independen dari Mapping (teammate manual majukan stage lewat UI CRM tim langsung, atau lewat "Record customer details"/promote candidate langsung di `/lead-engine`) — kalau sync berikutnya jalan dan tag Mapping-nya masih bilang stage yang lebih rendah, lead itu bisa tertimpa turun. Ini persis penyebab insiden 2026-09-28/29 (14 lead di "prospek" nyaris diturunkan ke "kontak"). Implementasi aman:
1. Sebelum PATCH stage, selalu **baca dulu** stage lead itu saat ini di CRM tim (`GET /api/leads`).
2. Bikin urutan ranking eksplisit: `prospek(1) < kontak(2) < demo(3) < uji_coba(4) < konversi(5)`, dengan `batal` (Lost) diperlakukan sebagai state terpisah/tidak diberi ranking (jangan pernah auto-override `batal` dari sync — itu keputusan manual sales, dan jangan juga auto-set ke `batal` kalau CRM tim sudah bukan `batal` lagi, kecuali memang tag Mapping-nya `declined`/`Reject` — di titik ini masih perlu keputusan tambahan kalau kasusnya muncul nyata: apakah `batal` boleh di-overwrite oleh sync kalau tag Mapping-nya berubah jadi tidak-Lost lagi. **Belum diputuskan, belum jadi masalah nyata sejauh ini — tangani kalau kasusnya benar-benar muncul.**)
3. Cuma PATCH kalau target rank **lebih tinggi** dari rank saat ini (atau kalau lead belum ada sama sekali di CRM tim — promote dulu, baru stage sesuai tabel).
