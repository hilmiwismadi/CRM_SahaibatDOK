# 11. Backup Database CRM (VPS → lokal, otomatis)

Dipasang 2026-10-07. Tujuan: database CRM di VPS (leads, pesan WA, scrape job, label, sync harian) berisi hasil kerja berbulan-bulan, jadi harus ada salinan **di luar VPS** yang terus diperbarui tanpa perlu diingat. Akses SSH dan aturan deploy ada di [[10.VpsAccessAndDeploy]].

## Gambaran

```
VPS (cron, 4x sehari)                          Laptop (Task Scheduler, tiap 2 jam)
scripts/backup-db.sh                           scripts/pull-vps-backups.ps1
  pg_dump -Fc  → *.tmp                           ssh: daftar file *.custom di VPS
  pg_restore -l (verifikasi)                     scp: unduh yang belum ada (*.part → rename)
  rename → ~/Mapping/backups/auto/               pangkas salinan lokal lama
```

Sengaja **pull dari laptop**, bukan push dari VPS: VPS tidak perlu menyimpan kredensial ke laptop, dan laptop yang sempat mati/offline tinggal mengejar file yang terlewat saat nyala lagi.

## Di VPS

| Item | Nilai |
|---|---|
| Skrip | `~/Mapping/scripts/backup-db.sh` (sumber: `Mapping/scripts/backup-db.sh`) |
| Jadwal | crontab user `DzakiWismadi`: `5 0,6,12,18 * * *` (WIB, 00:05 / 06:05 / 12:05 / 18:05), baris bertanda `# sahaibat-db-backup` |
| Lokasi | `~/Mapping/backups/auto/` |
| Log | `~/Mapping/backups/auto/backup.log` (hasil tiap run) dan `cron.out` (stderr cron) |
| Format | `pg_dump -Fc` (custom, terkompresi, bisa restore sebagian), ±18 MB per file saat 4.705 leads |

Retensi (di dalam skrip, bisa diubah lewat env `KEEP_ALL` / `KEEP_DAILY` / `KEEP_WEEKLY`):

| Folder | Isi | Disimpan |
|---|---|---|
| `auto/` | setiap run | 28 terbaru (±7 hari) |
| `auto/daily/` | run pertama tiap hari | 60 terbaru |
| `auto/weekly/` | run pertama tiap Minggu | 26 terbaru |

Perkiraan pemakaian disk VPS: ±(28+60+26) × 18 MB ≈ 2 GB (disk bebas saat dipasang: 21 GB). Pantau kalau DB tumbuh besar.

Cara kerja yang menjaga file tetap sehat:
- Dump ditulis ke `*.tmp`, diverifikasi dengan `pg_restore -l`, baru di-rename ke `*.custom`. File setengah jadi atau korup tidak pernah punya nama `*.custom`, jadi tidak ikut tertarik ke lokal.
- `flock` mencegah dua backup berjalan bersamaan.
- Run gagal → baris `FAIL ...` di `backup.log` dan exit code ≠ 0; file lama tidak tersentuh.

Backup manual `*.custom` lama di `~/Mapping/backups/` (mis. `mapping_dump_..._pre_sync_feature.custom`) dan `pre-import-20261007/` tidak dikelola skrip ini dan tidak ikut dipangkas.

## Restore

Selalu restore dulu ke **database sementara** untuk melihat isinya; jangan langsung menimpa produksi.

**Uji / lihat isi (aman)** — contoh ke Postgres lokal (`mapping-db-1`, port 5433), seperti yang dipakai saat verifikasi:
```bash
cd /d/Hilmi/Coding/Sahaibat/Backups/vps-crm-db/auto
F=$(ls -1t db_*.custom | head -1)
docker exec mapping-db-1 psql -U sahaibat -d postgres -c "CREATE DATABASE restore_test"
docker exec -i mapping-db-1 pg_restore -U sahaibat -d restore_test --no-owner < $F
docker exec mapping-db-1 psql -U sahaibat -d restore_test -c "select count(*) from leads"
docker exec mapping-db-1 psql -U sahaibat -d postgres -c "DROP DATABASE restore_test"
```
Hasil uji 2026-10-07: `leads=4705`, `wa_messages=6840`, `scrape_jobs=21` — sama dengan produksi.

**Pulihkan produksi (darurat)** — ini menimpa data, lakukan hanya dengan persetujuan eksplisit:
1. Ambil dump baru kondisi sekarang dulu (`~/Mapping/scripts/backup-db.sh`) supaya ada jalan kembali.
2. Salin file pilihan ke VPS (`scp`), hentikan `web` dan `wa-bridge` (`docker compose stop web wa-bridge`) agar tidak menulis saat restore.
3. `docker exec -i mapping-db-1 pg_restore -U sahaibat -d sahaibat_mapping --clean --if-exists --no-owner < file.custom`
4. `docker compose start web wa-bridge`, lalu cek `select count(*) from leads` dan buka `/map`.
Jangan pernah `docker compose down -v` (menghapus volume DB `mapping_db-data`).

## Mengubah / mencabut

- **Ubah jadwal VPS:** `crontab -e` (baris `# sahaibat-db-backup`), atau jalankan ulang pemasangan di bawah.
- **Ubah retensi:** edit default di `backup-db.sh` lalu `scp` ulang, atau set env di baris cron (`KEEP_DAILY=90 ...`).
- **Pasang ulang cron (idempoten):**
  ```bash
  LINE="5 0,6,12,18 * * * $HOME/Mapping/scripts/backup-db.sh >> $HOME/Mapping/backups/auto/cron.out 2>&1  # sahaibat-db-backup"
  (crontab -l 2>/dev/null | grep -v sahaibat-db-backup; echo "$LINE") | crontab -
  ```
- **Matikan di VPS:** `crontab -l | grep -v sahaibat-db-backup | crontab -`.
- **Matikan di laptop:** `Unregister-ScheduledTask "Sahaibat CRM DB Backup Pull" -Confirm:$false`.
- **Pasang ulang task laptop:** lihat `Register-ScheduledTask` di riwayat sesi 2026-10-07 — pada intinya trigger *AtLogOn* + *Once* dengan `-RepetitionInterval 2 jam`, action `pwsh -NoProfile -WindowStyle Hidden -File ...\pull-vps-backups.ps1`, setting `StartWhenAvailable`.

## Catatan pemasangan 2026-10-07

- Bug yang ketemu dan sudah diperbaiki saat uji pertama: folder `weekly/` kosong membuat `ls` gagal dan `pipefail` menggagalkan run (exit 2) walau dump-nya sukses. Sekarang `prune` menelan error "tidak ada file".

- Run terjadwal pertama yang sebenarnya: 00:05 WIB 2026-10-08. Cek `backup.log` pagi harinya untuk memastikan cron benar-benar jalan.
