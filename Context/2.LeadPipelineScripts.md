# 2. Lead Pipeline Scripts

Ringkasan isi `Mapping/scripts/` per 2026-09-21 — apa yang sudah pernah dibuat di sana, urutan pemakaiannya, dan status/known issues masing-masing.

## Arsitektur: 3 sistem terpisah, jangan tertukar

Ini koreksi penting yang sempat salah dipahami (lihat percakapan 2026-09-21) — ada **tiga** basis data berbeda yang semuanya nyangkut ke kata "CRM":

1. **CRM pribadi — local** (`localhost:5433`, app "Mapping" jalan di laptop). Punya database sendiri, dipakai buat scraping/testing.
2. **CRM pribadi — VPS** (`103.93.162.31:3000`, app "Mapping" yang sama, di-deploy ke VPS pribadi milik user — SSH key di `VPS_DW/DWSSH.pem`, container `mapping-db-1`). **Bukan CRM tim** meskipun di-hosting di VPS — ini instance kedua dari app yang sama, datanya sebagian besar mirror dari local (UUID lead manual identik di keduanya untuk baris yang sama).
   - Kedua instance Mapping ini pakai `pipeline_stage`: `new → contacted → responded → meeting_aligned → client_deciding_trial → trial_rejected/trial_accepted → offer_payment`.
3. **CRM tim — `sales.sahaibat.com`** (`/crm`, `/lead-engine`). Ini yang sebenarnya dipakai tim sales, app **terpisah total**, di-hosting di Vercel, login via NextAuth. Tidak ada akses DB langsung — satu-satunya jalan masuk adalah API-nya sendiri (`/api/leads`, `/api/lead-candidates`) lewat sesi browser yang sudah login (lihat `crm-stage-sync.js` / `crm-team-sync.js`).
   - Alur di sini: candidate mentah masuk lewat `/lead-engine` (upload/paste CSV atau discover), lalu di-**promote** jadi lead CRM asli.
   - Stage lead CRM: `kontak`, `prospek`, `demo`, `batal` (beda vocabulary dari Mapping — jangan disamakan).

**Intinya:** data yang masuk/berubah di Mapping (baik local maupun VPS) **tidak otomatis muncul** di `sales.sahaibat.com`. Harus disinkronkan manual lewat script yang jalan di browser console (karena tidak ada akses DB ke sana).

## Alur kerja (urutan pipeline, sumber lead baru)

1. **`run-scrape.ps1`** / **`run-scrape.sh`** — jalankan `gosom/google-maps-scraper` untuk satu atau lebih query, tulis hasil JSON ke `scrape-output/<name>.json`. Setelah itu diimpor manual lewat admin UI ("Scrapes" page) atau `POST /api/admin/import-staging`. Lihat `docs/SCRAPER_GUIDE.md` untuk referensi flag.
2. **`import-manual-batch.mjs`** — one-off script untuk impor batch lead manual (klinik/dokter area Yogyakarta/Semarang) ke CRM pribadi via `POST /api/leads`. Ada logic `classifyPhones` untuk membedakan nomor HP (prefix 81/82/83/85/87/88/89) vs telepon kantor/landline.
3. **`merge-manual-batch-geocode.mjs`** — pass 1: gabungkan `scrape-output/manual-batch-20260906.json` (hasil scrape gosom) ke lead manual dari langkah 2, dicocokkan berdasarkan nama persis (exact title match). Hanya mengisi lat/lng/address/category/googleMapsUrl yang masih kosong; tidak pernah mengubah `google_place_id`. Tidak pernah mencatat/print isi review.
4. **`merge-manual-batch-geocode-pass2.mjs`** — pass 2, lebih konservatif: untuk lead yang masih belum ada lat/lng setelah pass 1, coba cocokkan setelah kata generik (klinik, pratama, praktik, dst.) dibuang — hanya diterapkan kalau hasilnya unik (menghindari salah tempel kalau ada beberapa klinik dengan nama mirip di kota berbeda).
5. **`apply-instagram-links.mjs`** — tempel URL Instagram (dari mapping manual `IG_MAP` di dalam script) ke lead yang sudah punya `leadId` dan flag `hasIG` di `manual-batch-results.json`, via `PUT /api/leads/{id}`.
6. **`crm-stage-sync.js`** — script pertama yang menyasar CRM tim (`sales.sahaibat.com`), untuk **dipaste ke browser DevTools Console** saat login. Untuk 82 lead di daftar `MY_LEADS` (batch 2026-09-14): promote candidate → lead kalau perlu, lalu set stage "kontak" (5 nomor di `DEMO_PHONES` → "demo"). Konfirmasi 2026-09-21: stage `kontak`/`demo` itu memang valid di `sales.sahaibat.com` (bukan bug seperti sempat dikira — sebelumnya salah dicek ke database Mapping yang stage-nya beda vocabulary). Digantikan oleh `crm-sync/crm-team-sync.js` di poin 7 untuk sync berikutnya — file ini tetap di root `scripts/` sebagai arsip batch pertama, tidak dipakai lagi.
7. **`crm-sync/`** — folder khusus untuk sinkronisasi CRM pribadi → CRM tim yang berulang (lihat SOP lengkap di bawah). Isinya:
   - `crm-team-sync.js` — versi umum/berulang dari `crm-stage-sync.js`: promote-if-candidate, stage-if-needed, aman di-re-run. `MY_LEADS` diupdate tiap sync sesuai lead terbaru.
   - `build-import-csv.mjs` — Node script, ubah hasil query SQL (JSON) jadi CSV format `/lead-engine` — otomatis narik `city`/`province` dari string `address` (regex `Kabupaten X`/`Kota X`), jadi tidak perlu lagi dikerjakan manual satu-satu.
   - `sync-log.json` — catatan tiap sync: tanggal, jenis query yang dipakai, dan hasilnya (`alreadyOk`/`notFound`/`imported`/`staged`/`conflicts`). `lastSyncAt` di sini yang jadi patokan tanggal untuk query incremental berikutnya.
   - `imports/<tanggal>.csv` — arsip CSV yang benar-benar sudah dipaste ke `/lead-engine`, satu file per tanggal sync.

## SOP: Sinkronisasi CRM pribadi → CRM tim

Semua file kerja ada di `Mapping/scripts/crm-sync/`. Karena kedua sistem terpisah total (lihat bagian Arsitektur di atas) dan tidak ada akses DB ke CRM tim, prosesnya selalu manual lewat browser — tapi bagian query & CSV-nya sudah dibantu script.

### Langkah 1 — Cek kapan sync terakhir, lalu query CRM pribadi (HANYA DATA TERBARU)

Buka `crm-sync/sync-log.json`, lihat field `lastSyncAt`. **Jangan pernah** query ulang "semua lead yang statusnya sudah lewat `new`" — itu query snapshot yang cuma dipakai sekali di awal (2026-09-21), isinya makin lama makin besar dan penuh entri yang sudah pernah diproses. Pakai salah satu query incremental ini:

- **Berdasarkan kapan lead di-update terakhir** (default, ganti `<lastSyncAt>` dari `sync-log.json`):
  ```sql
  SELECT name, replace(coalesce(phone_normalized,''),'+62','0') AS phone_mobile,
         regexp_replace(coalesce(phone_office,''),'[^0-9]','','g') AS phone_office
  FROM leads
  WHERE pipeline_stage <> 'new' AND updated_at > '<lastSyncAt>'
  ORDER BY name;
  ```
- **Berdasarkan aktivitas chat WA hari itu** (cocok untuk sync harian/ad-hoc, "siapa yang baru saja saya chat"):
  ```sql
  SELECT DISTINCT l.name, replace(coalesce(l.phone_normalized,''),'+62','0') AS phone_mobile,
         regexp_replace(coalesce(l.phone_office,''),'[^0-9]','','g') AS phone_office
  FROM wa_messages wm
  JOIN wa_contacts wc ON wc.id = wm.wa_contact_id
  JOIN leads l ON l.id = wc.lead_id
  WHERE wm.sent_at::date = CURRENT_DATE
  ORDER BY l.name;
  ```

Jalankan via SSH ke VPS: `ssh -i VPS_DW/DWSSH.pem DzakiWismadi@103.93.162.31 "docker exec -i mapping-db-1 psql -U sahaibat -d sahaibat_mapping" <<'SQL' ... SQL`.

Alasan aturan "hanya data terbaru" bukan cuma soal performa — `MY_LEADS` yang terus membengkak dengan entri lama juga bikin `KNOWN_CONFLICTS` gampang kelewat pas nambah entri baru (lihat insiden 2026-09-22 di bagian Known issues, di mana entri lama yang belum dibersihkan dari `MY_LEADS` ke-run ulang dan nabrak konflik yang sebenarnya sudah diketahui).

### Langkah 2 — Jalankan `crm-team-sync.js`, catat siapa `notFound`

Update `MY_LEADS` di `crm-sync/crm-team-sync.js` dengan hasil langkah 1 (name + norm_phone), lalu paste seluruh isi file ke DevTools Console di `sales.sahaibat.com` (harus sudah login). Baca laporannya:
- `alreadyOk` — sudah benar, tidak perlu apa-apa.
- `notFound` — belum ada sama sekali sebagai lead atau candidate di CRM tim. Lanjut ke langkah 3.
- `duplicateConflict` — **jangan pernah di-retry**. Lanjut ke langkah 4.

### Langkah 3 — Bikin CSV cuma untuk yang `notFound`, pakai `build-import-csv.mjs`

Query ulang di database CRM pribadi, tapi kali ini **cuma nama-nama yang `notFound`** (bukan seluruh batch), dan minta output JSON langsung (hindari masalah koma-di-nama seperti "Dr tri yuli pramana,sp pd-kgeh"):
```sql
SELECT json_agg(row_to_json(t)) FROM (
  SELECT name, category, coalesce(province,'') AS province, coalesce(address,'') AS address,
         replace(coalesce(phone_normalized,''),'+62','0') AS phone_mobile,
         regexp_replace(coalesce(phone_office,''),'[^0-9]','','g') AS phone_office
  FROM leads WHERE name = ANY(ARRAY['Nama Satu','Nama Dua', ...])
) t;
```
Simpan output ke `crm-sync/staging/<tanggal>.json` (folder `staging/` di-gitignore, cuma tempat kerja sementara), lalu:
```
node crm-sync/build-import-csv.mjs crm-sync/staging/<tanggal>.json crm-sync/imports/<tanggal>.csv
```
Skim hasilnya — script akan bilang berapa baris yang `city`-nya gagal ke-derive (address-nya tidak match pola "Kabupaten X"/"Kota X"), perbaiki manual kalau ada. Paste isi CSV ke "Import candidates (CSV)" di `/lead-engine`, klik "Score & import". Re-run `crm-team-sync.js` (langkah 2) — yang baru diimpor sekarang akan ke-promote + ke-stage.

### Langkah 4 — Proses `duplicateConflict`

Untuk tiap entri di `duplicateConflict`, pindahkan dari `MY_LEADS` ke `KNOWN_CONFLICTS` di `crm-team-sync.js`, dan tandai `kind`-nya:
- `"teammate-ownership"` — `conflict.owner` itu email teman satu tim lain. Bentrok kepemilikan asli (misal klinik jaringan pakai satu nomor hotline untuk semua cabang) — perlu dikoordinasikan manual dengan pemiliknya, script tidak bisa menyelesaikan ini.
- `"own-lead-wrong-name"` — `conflict.owner` itu email sendiri (`hilmi.d@sahaibat.com`). **Bukan** konflik kepemilikan, tapi indikasi data scrape yang salah — nomor telepon yang sama ke-assign ke dua nama bisnis berbeda. Perlu dicek manual di `/crm` mana nama yang benar, lalu diperbaiki/di-merge di sana — bukan sesuatu yang bisa diperbaiki dengan menjalankan script ulang.

### Langkah 5 — Tutup dengan update `sync-log.json`

Tambahkan satu entri baru ke array `runs` (tanggal, jenis query, jumlah `alreadyOk`/`notFound`/`imported`/`staged`/`conflicts`, path CSV di `imports/`), dan update `lastSyncAt` ke tanggal hari ini. Ini yang dipakai langkah 1 di sync berikutnya.

**2026-09-28** — query "chat hari ini" lagi (25 lead dichat; 11 sudah ada, 14 benar-benar baru) → `crm-sync/imports/2026-09-28.csv`. **Temuan penting: perilaku "Score & import" di `/lead-engine` berubah** — sebelumnya (batch 09-21/22/24) hasil import masuk sebagai *candidate* dulu, baru di-promote+stage manual ke "kontak" lewat `crm-team-sync.js`. Sejak batch ini, "Score & import" langsung membuat **lead** di stage **"prospek"** (lebih maju dari "kontak"), tanpa lewat status candidate sama sekali — dikonfirmasi lewat `/api/leads` tepat setelah paste, semua 14 baris langsung muncul sebagai lead stage `prospek`. Konsekuensi: 14 lead batch ini **sengaja tidak ditambahkan ke `MY_LEADS`** di `crm-team-sync.js`, karena logic promote+stage script itu men-target stage "kontak" — kalau dijalankan untuk lead yang sudah "prospek", scriptnya akan **menurunkan** stage-nya balik ke "kontak", bukan cuma no-op. Satu baris ("Dokter BUDI HARTOYO, Jaten, Karanganyar", 08122982917) sempat error `"duplicate"` saat submit (kemungkinan double-submit) tapi dikonfirmasi tetap ada di stage "prospek" — tidak ada data hilang, tidak perlu tindakan lanjut. Kalau perilaku "Score & import" ini stabil (langsung ke "prospek"), langkah "notFound → build CSV → crm-team-sync.js" di SOP di atas kemungkinan besar perlu direvisi supaya tidak lagi promote+stage-kontak lead yang sudah diimpor lewat jalur ini — belum diubah di dokumen ini sampai dikonfirmasi konsisten di batch berikutnya.
